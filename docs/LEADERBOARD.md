# Спидран-лидерборд

DETACHED HEAD — stateless-игра: каждый узел это markdown-файл со ссылкой,
клик по эмодзи = переход. Поэтому спидран здесь — не таймер, а **маршрут**:
строка ходов, записанная токенами. Валидатор прогоняет маршрут по графу
`data/graph.json` и считает клики.

## Формат Issue

Открой Issue, в заголовке которой:

```
/run FFRRFX
```

- `/run` — префикс (регистр не важен: `/RUN`, `/Run` тоже работают);
- дальше — маршрут токенами `F` `B` `L` `R` `X` (см. таблицу ниже);
- регистр токенов не важен, пробелы и запятые игнорируются: `f, xr f` = `FXRF`;
- тело Issue может быть пустым — оно не разбирается;
- **игрок = автор Issue** (по логину).

| Токен | Действие |
|---|---|
| `F` | шаг вперёд по направлению взгляда |
| `B` | шаг назад |
| `L` / `R` | поворот налево / направо (тоже клик!) |
| `X` | выстрел (убивает босса только в арене) |

Дальше всё делает GitHub Action (см. «Как работает Action»).

## Как считать клики

- 1 токен = 1 клик по эмодзи-ссылке. Повороты — полноценные клики: крутить
  головой дорого.
- Маршрут валиден, если, начиная с узла `start` из `data/graph.json`,
  применение токенов по одному приводит ровно в узел `WIN`.
- Ход в стену (в графе `null`), неизвестный токен, ход в несуществующий узел —
  маршрут отклонён. В ошибке указывается индекс токена (с нуля) и причина.
- Токены после победы недопустимы: у `WIN` нет ссылок, лишний токен =
  ошибка «moves into a wall».
- Победа не через узел `WIN` (маршрут закончился в обычном узле) = ошибка
  «run did not reach WIN».

## Где взять карту узлов

- `data/graph.json` — весь граф игры; формат описан в
  [docs/DESIGN.md](DESIGN.md) (раздел «Схема data/graph.json»).
  У каждого узла есть `moves` — куда ведёт каждый токен (`null` = стена).
  `meta.start` — точка старта, `win` — победный узел `WIN`.
- Планировать маршрут удобно по графу: ключ `key=1` открывает мерж-гейт,
  арена начинается с `hp=4`, каждый `X` в арене уменьшает `hp` на 1,
  выстрел при `hp=1` даёт `WIN`.

## Локальная проверка

Из корня репозитория (пакет не устанавливается, достаточно `PYTHONPATH=src`):

```bash
# проверить маршрут (напечатает OK/FAIL)
PYTHONPATH=src python -m detached_head.leaderboard "FFRRFX"

# явно указать граф
PYTHONPATH=src python -m detached_head.leaderboard "FFRRFX" --graph data/graph.json

# проверить и записать результат в LEADERBOARD.md (как это делает CI)
PYTHONPATH=src python -m detached_head.leaderboard --submit YOUR_LOGIN "FFRRFX"

# тесты валидатора
PYTHONPATH=src python -m pytest tests/test_leaderboard.py
```

## Как работает Action

`.github/workflows/leaderboard.yml`, триггер — `issues: opened`:

1. Если заголовок НЕ начинается с `/run` — workflow молча выходит.
2. Маршрут = остаток заголовка после `/run`; передаётся в скрипт через
   env (без подстановки в команду).
3. `PYTHONPATH=src python -m detached_head.leaderboard --submit <login> <route>`
   валидирует маршрут по `data/graph.json`.
4. Валидный run: коммит `LEADERBOARD.md` в ветку по умолчанию (сообщение
   `leaderboard: @<login> <N> clicks [skip ci]`, автор github-actions[bot]),
   комментарий с местом игрока и таблицей, Issue закрывается.
5. Невалидный run: комментарий с текстом ошибки и индексом токена, метка
   `invalid-run`, Issue закрывается.

Таблица `LEADERBOARD.md` живёт между маркерами
`<!-- LEADERBOARD:BEGIN -->` и `<!-- LEADERBOARD:END -->`; всё вне маркеров
Action не трогает. Сортировка: по кликам по возрастанию, при равенстве — по
дате. У одного игрока хранится только лучший результат (меньше кликов);
повторная отправка худшего маршрута ничего не меняет.
